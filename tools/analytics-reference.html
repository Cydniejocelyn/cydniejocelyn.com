How to read this

Event names are snake_case and under forty characters, which is what GA4 requires. Four of the twelve use names Google itself defines — those are marked GA4 recommended — and that matters more than it sounds: a recommended event populates the built-in reports in the Google interface, where a custom name only ever appears in an exploration you build yourself.

Every event also carries page_path. Parameter values are collapsed to single spaces and truncated at 100 characters, which is GA4's own limit; a truncated value ends in an ellipsis so it is obvious in a report that there was more.

Navigation and intent

navigation_click

A link in the header, the mobile menu, the footer, the legal row, the social row, the brand lockup or the skip link.

Fires on every page. nav_location is the useful half: “Retreats” clicked in the header is a person navigating, and the same word clicked in the footer is usually a person who read to the bottom. The header and the phone panel are the same markup, so they are told apart by the 56rem media query — the same one site.js uses, so the two can never disagree.

  • link_text
  • link_url
  • nav_location
cta_click

A .btn, or any link to the booking system, wherever it sits.

Fires on every page. Held apart from navigation_click on purpose: a button is a considered decision and a nav link is a glance, and putting them in one number dilutes the funnel with chrome. cta_location is the nav region for chrome buttons and the enclosing section id for in-page ones.

  • cta_text
  • cta_location
  • link_url
  • destination_type
outbound_click

Any click that leaves the site.

Fires in addition to the event above, never instead of it. A booking link is both a call to action and an exit, and collapsing the two would mean choosing now which question you are allowed to ask later. destination_type separates booking from external, so the client portal does not sit in the same bucket as a link to Instagram.

  • link_url
  • link_domain
  • link_text
  • nav_location
menu_toggle

The two-bar menu control opening or closing.

Fires on eight pages; /thequestions/ has a bare header with no toggle. Read on the capture phase so it reports the state being moved into. On the bubble phase site.js has already flipped aria-expanded, and every open reads as a close.

  • menu_state
  • viewport

Content interaction

filter_select

One of the four tabs in the objection picker.

Home and Greece. This is the site's only filter: four tabs, one panel shown at a time. filter_position tells you whether people work through them in order or go straight to the one that is their own objection, which is the more useful question.

  • filter_group
  • filter_value
  • filter_position
  • filter_count
image_view

A gallery tile opened into the lightbox.

Greece only. Carries the caption rather than the filename, so a report reads as “Your room” instead of a hash.

  • image_caption
  • gallery_name
  • image_position
gallery_navigate

The forward and back arrows on the photograph rail.

Greece only. Separate from image_view because browsing the rail and stopping to look at one photograph are different degrees of interest.

  • direction
  • gallery_name
content_step

A tick on the five-moment story scroll.

Home and Greece. Only counts a deliberate press, not the scroll position moving the story on by itself.

  • step_index
  • step_count
  • step_label
faq_open

A question opening.

Home, The Build, Retreats, Greece and A Sounding. Closing one is not counted — a close is not a signal about anything. The question text comes through verbatim, which turns this into a standing list of what people actually needed to ask.

  • question_text
  • question_position
  • question_count
video_startGA4 recommended

The testimonial video being pressed.

Retreats only. The poster is an anchor with a real YouTube href so it works without JavaScript, but with JavaScript it never navigates — so it is deliberately not counted as an outbound click. Read on the capture phase, for the same reason as the menu toggle.

  • video_title
  • video_provider
  • video_url
  • video_current_time

Reading depth and conversion

scroll_depth

25%, 50%, 75% and 100% of the page, once each per page load.

Fires on the eight long pages and is deliberately silent on /thequestions/, which is a single screen scanned at a table. On a page barely taller than the window, 100% is reached by existing, and four events that always fire together say nothing. The gate is one and a half viewports of scrollable content. Scrolling back up and down again does not fire anything a second time.

  • percent_scrolled
  • page_length_px
  • viewports
sign_upGA4 recommended

The Letters signup being submitted.

The Letters only. The Flodesk widget cancels the native submit and posts over fetch, so this listens on the capture phase at document level — a bubble-phase listener on a form that never natively submits can be skipped entirely. Fires at most once per page load.

  • method
  • form_destination
  • form_location

One caveat worth stating plainly: sign_up records the attempt, not the confirmed subscription. Flodesk owns everything after the submit, and it does not tell the page whether the address was accepted. Treat this number as the top of that step and Flodesk's own list count as the bottom of it.

Two things that were asked for and are not here

Copy-to-clipboard on code samples

There is no code on this site. Not one <pre>, one <code>, or one clipboard call across the nine pages — it is a consulting practice, not a documentation site. Nothing was invented to fill the gap, because a tracker firing on an element that does not exist is a number nobody can act on.

Filter and search on component listings

There are no component listings and no search input either. The nearest real equivalent is the four-tab objection picker, and it is genuinely a filter — one of four choices decides which panel shows — so it is tracked as filter_select with the parameter names a filter would have. The gallery rail and the lightbox are tracked as themselves rather than being dressed up as a listing.

If a component library, a resource index or a search ever gets built, both patterns drop straight into analytics.js: the click tracking is delegated off document, so new markup is picked up with no rewiring.

Checking it yourself

  1. Open any page, then in the browser console set __analyticsDebug = true. Every event prints as it fires, with its parameters, before it is sent.
  2. In Google Analytics, use Admin → DebugView. It shows events within seconds; the standard reports take up to 24 hours and have made more than one person think tracking was broken when it was only slow.
  3. Run the automated pass, which drives every interaction on every page and asserts what came out:
sh tools/preview/runga.sh "$SP" 8817

That harness runs in headless Chrome and not in a preview pane, for a specific reason: a preview pane moves the page when you set scrollTop and fires no scroll event at all, so every depth assertion fails against code that is perfectly correct. The harness prints a diagnostic line saying so, rather than leaving the next person to rediscover it.

What is deliberately not collected

  • Nothing anyone types. No field values, no email addresses, no search terms. sign_up records that a form was submitted and nothing that was in it.
  • No individual identity. No user ID, no cross-device stitching, no advertising features. The two cookies are _ga and _ga_KDB3GWPNHC, and both are named in the privacy policy.
  • No scroll heatmap or session recording. Four depth thresholds is a measure of whether a page holds attention; a recording is a different thing to consent to.

Readers running an ad blocker send nothing, which is normal and is not an error state — expect the totals here to under-count a design-literate audience by a noticeable margin. And the site currently takes the implied-consent posture: analytics loads before anyone agrees to it. That is standard for a US business and it is not GDPR consent, which is worth a decision of its own if the Greece retreat draws European traffic.
