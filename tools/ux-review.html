Nine Frictions

Where the interface asks more of a reader than it needs to — measured on the built site at 375 and 1440, and ordered by how much each one costs.

All nine are now fixed and shipping. This page is kept as the record of what was wrong and why, because the reasoning is the part worth having later — each fix carries its measurement in the code beside it. Two are marked Part below: the half of each that was a design or copy decision rather than a defect was deliberately left for Cydnie, and is named.

Verified after: the behaviour suite went from 356 to 385 assertions, 0 failing, across all nine pages. Six of the new ones exist to stop these specific frictions coming back silently.

Before the list

This site is built better than most. Every interactive element has a keyboard path: Escape closes the menu and the lightbox, arrow keys move the tabs, the ticks and the gallery, focus is trapped inside the lightbox and handed back to the tile that opened it. There is one h1 per page, no heading skips, alt text on every image, and motion is switched off under prefers-reduced-motion. Tap targets that look too small mostly are not — the door links grow theirs with a pseudo-element, which is a more careful answer than a min-height.

So the list below is not a list of things anyone was careless about. Seven of the nine are places where a decision that is right in one context was applied in a second one where it stops working — a hover cue on a touch screen, a colour picked for a dark ground appearing on a light one, a rule written for the phone menu never reaching the desktop bar.

Everything here was measured rather than eyeballed. Contrast figures are WCAG 2.x ratios computed from the rendered colours on the built pages.

The findings

1.00:1link vs the text around it

Fixed

1. Links inside sentences are invisible until you hover them

Every .link in body copy draws its underline only on hover: at rest the pseudo-element sits at scaleX(0). That would be fine if colour carried it, and colour does not. On the home page “Watch Melissa’s review” measures 1.16:1 against the sentence it sits in, and hello@cydniejocelyn.com measures 1.00:1 — the identical colour. “retreats page” and “Read the letters” measure 2.49:1.

Why it mattersThese are not decorative links. They are the in-copy routes to the retreats page, The Letters, and the testimonial video — the exact moments where the writing has just earned a click. On a phone there is no hover at all, so on more than half the traffic these are simply not links. It is also the one clear WCAG failure on the site (1.4.1 Use of Colour, which wants 3:1 against surrounding text when colour is the only distinction — here there is not even colour).

The fixDraw the underline at rest and change it on hover, instead of drawing it on hover. The mechanism already exists — .link--ruled is exactly this and is used on the privacy page. Making --ruled the default and keeping the hover flourish as the change of state is a one-rule edit: 

.link::after { transform: scaleX(1); transform-origin: left; }
.link:hover::after,
.link:focus-visible::after { transform: scaleX(0); transform-origin: right; }

1.36:1focus ring on Silt

Fixed

2. The focus ring vanishes on every light section

The global rule is :focus-visible { outline: 2px solid var(--breath) }. Breath is a colour chosen for a dark ground, and it is superb there — 10.14:1 on Fathom. On the two light bands it measures 1.47:1 on Surface and 1.36:1 on Silt. On the home page, 32 of 66 interactive elements sit on one of those two grounds.

Why it mattersA keyboard user tabbing down the home page watches the ring travel normally, then lose it completely for half the page, then find it again. That is worse than no ring at all, because the first half teaches them to expect one. WCAG 2.4.11 and 1.4.11 both want 3:1 here. It is also the single cheapest fix on this list.

The fixGive focus its own ground-aware token, the way --ink and --accent already are, rather than naming a raw swatch. Breath on the dark bands, Fathom on the light ones — measured 10.14:1 and about 15:1 respectively. Note that reusing --accent is not the answer: it resolves to Meniscus on dark, which is only 2.34:1. 

/* with the other role tokens */
--focus: var(--breath);              /* dark grounds */
.z-light, .z-silt { --focus: var(--fathom); }

:focus-visible { outline: 2px solid var(--focus); }

textthe email input’s type

Fixed

3. The signup asks for an email with a plain text field

The Letters form has exactly two visible fields, which is right. But the email input is type="text", not type="email", and carries no autocomplete.

Why it mattersOn a phone, type="email" is what summons the keyboard with @ and .com on the front layer. Without it every subscriber types an address on the general keyboard, switching layouts twice, with autocorrect live. It is the single highest-friction moment on the page the whole site funnels toward, and it costs typos as well as patience — a mistyped address is a subscriber who silently never arrives.

The fixThis is Flodesk’s markup, not the site’s, so it is a change in the Flodesk form builder rather than in this repo: set the field type to email. If Flodesk will not expose it, the alternative is their raw API behind a form written here, which is more work but also removes the two findings below it. Add autocomplete="email" and autocomplete="name" at the same time.

0live regions on the form

Fixed

4. A failed signup says nothing to a screen reader

Submitting the form empty renders “This field is required” on screen. There is no aria-live region, no role="alert", and aria-invalid is unset on every input. The message appears visually and is announced to nobody.

Why it mattersA screen reader user presses the button and receives silence. Nothing tells them the submission failed, so the reasonable conclusion is that it worked. This is the failure mode where someone believes they subscribed and did not, and there is no later signal to correct it. It is a smaller audience than finding 1, but the cost per person is total rather than partial.

The fixSame owner as finding 3 — Flodesk renders this markup. If their builder cannot add a live region, a small progressive enhancement in site.js can: observe the form for the error node the widget injects and mirror its text into a role="status" element on the page. That is a workaround, and it is worth saying plainly that the durable answer is owning the form.

1.00:1current page vs the others

Fixed

5. The navigation never shows which page you are on, at desktop

The markup is right: aria-current="page" is on the correct link on every page, so a screen reader announces it. The styling for it is not. All four rules that colour the current link live inside @media (max-width: 55.99rem) — the phone-menu block. At 1440 the current link and its neighbours measure 1.00:1: identical colour, identical weight, no underline, no rule.

Why it mattersNine pages, four nav items, and long pages that take twenty screens to read. A reader who arrives mid-site from a search result and scrolls for a while has no persistent answer to “where am I”. The bar is the only place that could tell them and it does not. The fix costs nothing because the design decision has already been made and written — it is simply scoped to the wrong widths.

The fixMove the [aria-current="page"] rules out of the phone-menu media block so they apply at every width. Worth checking the specificity when you do: the file already carries a note about .hdr.is-surfaced .nav-links a at (0,3,1) beating a (0,2,1) rule and blanking the menu once. A colour change alone is also WCAG 1.4.1 territory — pair it with the underline the hover state already draws, so it is not colour doing the work on its own.

14 / 14external links, none marked

Part

6. The button that matters most quietly hands the reader to somebody else

“A Sounding” in the header, and every “Book one conversation” on the site, navigate to clients.cydniejocelyn.com — HoneyBook’s scheduler, a different application with different typography — in the same tab, with no signal beforehand. All fourteen external links on the home page behave this way, social and video included.

Why it mattersFor a design-literate audience the jump is legible as a third-party tool immediately, and the site has spent twenty screens earning trust with a very specific voice. Landing somewhere that looks nothing like it, with no warning and the back button as the only way home, is where a considered decision becomes a hesitation. The scheduler is the right tool; the transition is the problem, not the destination.

The fixTwo different answers for two different links. Booking: keep it in the same tab — a purchase flow should not open a tab — but say where it goes, with a line under the button such as “Opens my scheduling page” and a matched accent colour on the HoneyBook side so the arrival is not a jolt. Social and video: these are genuine departures from a page someone was reading, and should open in a new tab with rel="noopener", which every one of them already carries.

What shipped, and what did notAll 38 social and video links open in a new tab now and say so. All 53 off-site links across the nine pages carry an announcement — including the one inside the Flodesk widget and the one in the Sounding popup, neither of which exists in any source file. The visible line under the booking button was not written. That is copy on nine pages and a change to the header composition, which is your call and not a defect. The screen-reader half is done at no visual cost; the visible half is a sentence away whenever you want it.

20.5screens on the Greece page

Part

7. The depth gauge looks like a control and is not one

A fixed 16px column sits at the left edge of every page, labelled “Resurfacing”, with an indicator that tracks scroll position. It is not interactive: no link, no button, no handler. The pages it sits beside run to 18,458px — 20.5 screens at a 900px viewport. There is no back-to-top and no section navigation anywhere.

Why it mattersA thin vertical track at the edge of the viewport with a moving marker is the most established scrubber pattern there is. It invites a drag, and on the longest pages it is exactly when someone would most want one. Nothing happens, which spends a little credibility for a design audience who read affordances closely. The gauge is a good idea reading as an unfinished one.

The fixPick one and commit. Either make it do what it looks like — click or drag to seek, with the section names as stops, which suits a page composed in named movements — or make it read as instrumentation rather than a control: drop the track, keep the label and a tick, and let it be a gauge. If it stays passive, add a back-to-top that appears past the first few screens, because at twenty screens the return journey is currently a long scroll or the brand mark.

What shipped, and what did notThe gauge takes pointer-events: none, so it no longer returns a cursor or a hover it cannot honour, and it can no longer swallow a click meant for the content behind it. A “Back to the top” link sits at the head of the footer on all nine pages — in the flow, using the existing .more idiom, not a floating button, because somebody who wants the top is already at the bottom. The gauge was not redrawn. Making it read as instrumentation rather than a track is a change to your visual identity on every page, and that is a decision rather than a fix.

3 / 16rail tiles visible at 1440

Fixed

8. The photo rail never says how much of it there is

The Greece gallery holds sixteen photographs. Three are visible at 1440, the rail scrolls 6,452px inside a 1,320px window, and it has working arrows and a progress rule. What it has nowhere is a number.

Why it mattersThe progress rule answers “roughly how far” but not “how much is there”, and those are different questions for someone deciding whether to commit to browsing. Sixteen photographs of a retreat is a genuine selling point on the page most likely to convert, and the interface currently undersells it. A reader who sees three and does not notice the affordance sees a three-photograph gallery.

The fixA live count beside the arrows — “3 / 16”, updated on scroll from the same handler that drives the progress rule. It is the same data already being computed, given a second, more readable output.

1questions open at once

Fixed

9. Opening one question closes the one you were reading

The accordions are exclusive: opening any question closes the previous one. This is deliberate and asserted in the test suite, so it is a decision rather than an accident.

Why it mattersExclusive accordions are right when the panels are long enough that two open ones would strand the reader. These are short — two or three sentences — and several are directly comparable: what a Sounding is against what The Build is, what is included against what is not. Someone answering “which of these do I want” has to hold one answer in their head while opening the other. The pattern is also the less expected of the two now; readers generally assume a question they opened stays open until they close it.

The fixAllow multiple open. It is a deletion rather than an addition — the handler that closes the siblings comes out, and the suite assertion changes with it. Worth doing on the pages where the questions are comparisons and leaving alone anywhere the panels are long.

What not to change

A few things that look like problems from the outside and are not, so they do not get “fixed” later by someone reading a generic audit:

  • The small-looking door links. Measured at 18px tall, which fails every tap-target rule — except the target is grown to 44px with .door-note--link::after { inset: -13px -10px }. A pseudo-element rather than a min-height, so it does not push the note out of alignment with its neighbours. That is the better answer and the reason is already in a comment beside it.
  • Inline text links being under 24px tall. WCAG’s target-size rule explicitly exempts targets inside a sentence. Finding 1 is about whether you can see them, not whether you can hit them.
  • The video that does not autoplay or preload. Click-to-load on youtube-nocookie is the right call twice over, for weight and for privacy, and the poster is a working link without JavaScript.
  • Smooth scrolling. Already switched off under prefers-reduced-motion, which is the part people usually miss.

And the hero headings did get bigger

Asked during this work: did something change? Yes, and it is measurable. The font-size was not touched — it is the same 69.6px at 1440 that it has always been, with the same line height. The typeface changed. IvyJournal replaced Instrument Serif as the carved face when the Adobe kit went in, and at an identical size IvyJournal is simply a larger letter:

At 100px, both facesInstrument SerifIvyJournalDifference
Cap height — governs all-caps lines like the hero66.272.8+10.0%
x-height — governs how large mixed-case type reads44.953.1+18.3%
Width of “YOU’RE NOT BROKEN.”1067.61130.0+5.8%

The x-height number is the one that explains the feeling. x-height, not point size, is what the eye reads as “how big is this type”, and an 18% jump at the same nominal size is very visible. Compounded with the 5.8% extra width, the home hero went from two lines to four at 1440.

If you want it back to where it wasNothing is broken, so this is a taste decision rather than a fix, and it is one number. Multiplying the carved type scale by 0.91 matches the old cap height, which is the right target for the all-caps hero. Matching x-height instead would want 0.85, which is right for mixed-case headings like “I’m Cydnie.” but would leave the hero looking smaller than it used to. If one figure has to serve both, 0.91 is the one to try first, and the hero should come back to two lines at 1440. Say the word and I will apply it and re-measure every heading at 375, 390, 768 and 1440.

If only three get done

That was the recommendation when this list was written, and all nine were done instead. Findings 1, 2 and 3 were the three that mattered most: the first two were single-rule CSS edits that between them fixed the site for touch readers and for keyboard readers without changing how anything looks to anyone else, and the third was the only one on the list actively costing subscribers.

Findings 3 and 4 share an owner. If the Flodesk builder will not expose the field type or a live region, that is the argument for writing the form here against their API — one piece of work that closes both, and gives the signup the same voice as the rest of the page rather than a widget’s.
